# Whiteboard Backend Runbook (Development Identity, Sessions, Invitations, and Realtime Access)

This runbook covers server-side email identity, board sessions, private invitation acceptance, authenticated WebSocket access, durable membership, ordered board edits, MongoDB operation/snapshot recovery, and transient connection leases. It is not a production deployment guide; deployment and multi-browser release gates remain open.

## Local setup

1. Configure `servers/api/.env` from `.env.example`; do not commit `.env` or copy secrets into this runbook. Keep the app/API host consistent (`localhost` for both) for the Lax session cookie. For production, use HTTPS and a stable 64-hex-character rate-limit key generated from 32 random bytes.
2. Set `MONGODB_URI` to the development Whiteboard database. API identity endpoints intentionally return service unavailable if persistence is not configured.
3. Set `WEB_ORIGIN` to the exact local Whiteboard app origin. The API compares it for browser mutation requests and uses it when building magic links.
4. For per-owner invitation email, create a Google Cloud OAuth Web application client. Configure the consent screen as External/Testing and add each local tester Gmail account. Enable Gmail API and request only `https://www.googleapis.com/auth/gmail.send`. Add `http://localhost:4000/auth/google-mail/callback` as an authorized redirect URI for same-computer use. Put `GOOGLE_OAUTH_CLIENT_ID`, `GOOGLE_OAUTH_CLIENT_SECRET`, and the exact `GOOGLE_OAUTH_REDIRECT_URI` in `servers/api/.env`. Generate the encryption key with `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"` and set it as `GOOGLE_TOKEN_ENCRYPTION_KEY`. Do not share or commit OAuth secrets or this key. In Whiteboard, each session owner signs in, selects **Connect Gmail** using the same Gmail address, grants permission, and then sends invitations from that account. If OAuth consent status is Testing, Google test-user authorization expires after seven days; reconnect when that happens. Keep the encryption key stable or all connected owners must reconnect. The localhost callback is for connecting accounts in a browser on the API machine; a LAN peer needs an HTTPS development tunnel/callback to connect from its own device.
   Optional shared `GMAIL_USER` and `GMAIL_APP_PASSWORD` settings are used only to send Whiteboard sign-in links. They do not send session invitations. Without these settings, development sign-in uses the local mailbox; invitation email still requires each owner to connect Gmail.
5. For same-computer use, keep `WEB_ORIGIN=http://localhost:3000`, API at `127.0.0.1:4000`, realtime at `127.0.0.1:4001`, and app variables `NEXT_PUBLIC_WHITEBOARD_API_ORIGIN=http://localhost:4000` and `NEXT_PUBLIC_WHITEBOARD_REALTIME_URL=ws://localhost:4001`.
6. To let a participant on another device on the same LAN open the emailed link, use the owner's LAN address consistently: set API `API_HOST=0.0.0.0`, `REALTIME_HOST=0.0.0.0`, `WEB_ORIGIN=http://<owner-lan-ip>:3000`, app `NEXT_PUBLIC_WHITEBOARD_API_ORIGIN=http://<owner-lan-ip>:4000`, and `NEXT_PUBLIC_WHITEBOARD_REALTIME_URL=ws://<owner-lan-ip>:4001`. Open the app as `http://<owner-lan-ip>:3000` on the owner and participant devices, allow the required local ports through Windows Firewall for the private network, and ensure both devices are on the same reachable network. `localhost` in an emailed URL points to the recipient's own device, so it is not valid for a second device. This LAN setup does not make the local app reachable to participants outside that network.
7. In a terminal run `pnpm --dir servers/api run dev` and in another run the Whiteboard app with its configured local port.
8. Check `GET http://127.0.0.1:4000/health`; the API log should also report the realtime host and port.

## HTTP request rate limit

The API uses MongoDB-backed fixed windows of 300 HTTP requests per minute per session-cookie bucket and 1,800 requests per minute per source-IP bucket. Requests without a valid session cookie use the IP bucket for both limits. The health route is exempt so monitoring remains available during a database outage. Session-cookie and IP values are HMACed with the configured `IDENTITY_RATE_LIMIT_KEY` before storage; no raw identifier is used as the rate-limit key. Every HTTP `429` includes `Retry-After` seconds. If the counter store cannot be checked, API requests fail closed with `503` while `/health` remains available. For a deployment behind reverse proxies, set `API_TRUST_PROXY_HOPS` to the exact number of trusted hops; the default is no proxy trust. Restrict direct access to the API so clients cannot bypass the trusted proxy chain.

**Signal/threshold:** HTTP request logs show `429`; occasional responses are expected when a client retries too aggressively. More than 30 `429` responses from the same network in five minutes is actionable. **Response:** check whether a client is looping or reconnecting repeatedly, inspect MongoDB/API health, and slow or fix the client. Do not raise the limit until the traffic is identified. The rate-limit middleware does not log session cookies or IP keys.

## Owner-ended session notification

When the owner-end request commits, the realtime server sends `session:ended` to each connected invitee immediately before closing that room's socket. The invitee app detaches from the deleted session and shows a popup; the current board remains local and unsaved. **Signal/threshold:** the popup should appear promptly when the owner finishes ending the session; a connected invitee who sees only a generic disconnect or still sees the session as active after five seconds is actionable. **Response:** confirm the owner end request succeeded, then inspect API/realtime logs and reconnect the invitee only to verify the ended room rejects access. The invitee can download XML from the retained local board. Offline invitees cannot receive the event while disconnected; their next attempt to restore the deleted session clears its stale session state.

## Two-identity realtime integration check

Run `pnpm --dir apps/whiteboard run test:realtime` against loopback API, WebSocket, and web-origin URLs only. The script refuses non-loopback destinations. It uses the development mailbox, reuses `wb-integration-owner@example.invalid` and `wb-integration-editor@example.invalid`, verifies each session cookie resolves to its expected API identity, accepts a private Editor invitation, opens two Hocuspocus clients with separate cookies, and verifies each participant receives the other's accepted board edit. It ends the temporary session in cleanup; the two synthetic identity records remain in the development database for reuse. It does not send real email or require the browser UI.

**Signal and threshold:** a successful run prints one `PASS` line and exits zero. Any nonzero exit, failed authentication, missing invitation, message rejection, or eight-second room-sync timeout is actionable. A magic-link `429` includes the response's `Retry-After` duration; do not rerun before it elapses. **Response:** verify MongoDB/API/realtime health and that `WEB_ORIGIN` exactly matches `WHITEBOARD_WEB_ORIGIN`; inspect API/realtime logs using the temporary session context. Never log or copy verification links, invitation tokens, cookies, or MongoDB credentials. If cleanup fails, end the synthetic session using the owner account or remove its temporary records through the normal owner-end path before retrying.

**Latest verification (2026-10-20):** The script passed with separate Owner and Editor identities, an accepted private invitation, authenticated Hocuspocus room membership, and two-way persisted edit broadcasts. It ended the temporary session. This verifies the API/provider integration but does not verify the browser sign-in confirmation or session-creation UI.

## Offline edit queue

The app shows connection state and the number of pending edits in the live-session status. The local queue allows at most 500 edits and 1 MB of serialized data; if the next gesture exceeds either limit, it is refused before board state changes. If transport drops while an edit is in flight, the client clears only the volatile in-flight marker, keeps the queued edit and stable action ID, authenticates again, reads canonical board state, and retries; server idempotency prevents a duplicate commit when only the acknowledgement was lost. Reconnect and retry the queue before continuing to edit. Queue items older than seven days stay in session-scoped localStorage but pause for explicit confirmation because replay may replace newer values. **Signal/threshold:** a pending count approaching 500 or the client message `Offline edit limit reached` means the device queue is full; any item older than seven days is also a review threshold. **Response:** restore the API/realtime connection, use **Retry queued edits**, and confirm the stale-replay prompt only after reviewing that an older local edit may replace current values. Never clear the queue or report those edits as server-saved until the server accepts them.

Live Collaboration supports Editor and Viewer roles. The owner must select a role for each invitation. Viewers are read-only for board content but navigate their own canvas; there is no separate Presentation mode or shared presentation viewport. Owner disconnect does not end the session or change participant viewports.

Live participant names, roles, and cursors come from Hocuspocus awareness in the authenticated session room. The server replaces client identity claims and removes cursor data for Viewers; awareness is transient and does not enter MongoDB board history or XML. **Signal/threshold:** the presence strip and Owner/Editor cursor should clear within the Yjs awareness expiry window (30 seconds) after disconnect; any Viewer cursor broadcast or stale participant remaining beyond 30 seconds is actionable. **Response:** verify Hocuspocus socket close/lease expiry and awareness updates, then reconnect the affected member; do not manually mutate durable membership to clear presence.

Each authenticated socket may send at most 1,200 awareness updates per 60 seconds and one client state per update. The API logs `Realtime awareness update rate limit exceeded.` at the first excess update, or `Realtime awareness update contained multiple client states; update dropped.` once for a malformed connection; offending awareness state is dropped. **Signal/threshold:** any such log is actionable because a legitimate client normally sends cursor updates below that limit. **Response:** identify the session/socket via the server logs and observe whether a buggy client is flooding updates; reconnect that client and investigate before changing the limit. Awareness payloads are not logged.

## Exercise the owner session API

### Session lifecycle (no time-based expiry)

Sessions remain active without a time-based expiry until the owner explicitly ends them. Existing legacy `mode` and `expiresAt` fields in MongoDB are ignored. There is no session-expiry background job. On owner end, access is revoked and temporary live records are cleaned up; a cleanup failure is logged and the owner can retry the end request. Atlas backups are governed separately by configured backup retention and are not covered by live-record deletion.

The app has a sign-in dialog and calls these routes. Set `NEXT_PUBLIC_WHITEBOARD_API_ORIGIN` in `apps/whiteboard/.env.local` to the API origin, and set API `WEB_ORIGIN` to the exact running app origin. The session routes require MongoDB and a verified identity cookie.

1. `POST /sessions` with the exact `Origin` and JSON containing `title` and a canonical `board` object from the Whiteboard editor. The verified cookie determines the owner; do not send a mode or owner ID.
2. Verify the response is `201` with `status: active`. Save its server-generated `session.id` for subsequent requests.
3. `GET /sessions/:sessionId` reads the session; `PATCH /sessions/:sessionId` with `{ "title": "..." }` renames it; `DELETE /sessions/:sessionId` ends it. Each mutation needs the exact `Origin` and valid cookie.
4. Use a second identity to check that GET/rename/end do not reveal or modify another owner's session. A missing or non-owned session returns safe `404`.
5. Session endpoints return `503` if MongoDB is not configured or unavailable. Do not interpret this as a successful local session.

For owner shutdown, use the app's **End session** dialog. **Download XML and End** first reads the canonical server board and sequence and starts the Whiteboard XML download. The owner then confirms the end separately, which sends the downloaded sequence with the end request. This lets the owner keep the session Active if the browser download is canceled. The API closes only if the accepted sequence still matches; a `409 session_revision_changed` means a newer edit arrived during export. The session remains Active, and the owner should download the latest revision again before confirming. **End without downloading** ends without the sequence precondition; **Cancel** leaves the session open. An export read/download failure leaves it open. **Signal/threshold:** any `409 session_revision_changed` or failed end/cleanup response is actionable. **Response:** re-download the latest revision; if the API reports cleanup failure after closure, retry End without downloading so the existing ended marker can finish retryable cleanup. Server logs identify cleanup stage and session ID.

These routes are called by the app. The implementation check also exercised identity verification and session create/read/rename/end against the configured development MongoDB using a reserved test address; it ended the test session. The automated route tests use deterministic in-memory repositories and identity resolution. A full browser confirm-link, reload-restore, and second-owner denial pass remains open.

## Exercise a private session invitation

1. Sign in as the session owner and start an Active session. Open **Invite participants**, enter the recipient email, and choose an explicit Editor or Viewer role for every invitation.
2. The API creates a cryptographically random token, stores only its SHA-256 hash, and sends a private **Accept invitation** email that expires in 10 minutes. The link token is in the URL fragment; the API response never contains it. Pending invitations do not reserve seats.
3. The invitee opens the email sent to the invited address, signs in using that same email, returns to the invitation page, enters a display name, and explicitly accepts. The API atomically consumes the invitation and records the server-side identity and fixed role. Reload on the same browser tab restores the active session snapshot.
5. Owner can list pending/unexpired invitations and cancel one before acceptance. Expired, canceled, used, wrong-email, or ended-session invitations cannot establish membership. Request an invitation again if delivery or expiry requires retry.
6. API limits invitation create/accept requests to 10 per identity and 30 per source IP per fixed 15-minute window. Excess returns `429`; inspect only hashed limiter keys and honor the window. The limit records share Mongo TTL cleanup with identity rate records.

Google OAuth lets each session owner send invitations through their own Gmail using the Gmail API; the shared Gmail App Password, if present, is only for sign-in links. OAuth refresh tokens are encrypted before MongoDB storage. Sending is synchronous with a 15-second timeout; there is no background retry. The realtime listener validates exact Origin, the verified `wb_session` cookie, active-session status, and owner/accepted membership before room entry. MongoDB keeps durable membership (owner plus up to 24 invitees; 25 members total) separate from transient socket leases. Pending invitations use no member slot; disconnect never removes membership. Invitation consumption and adding the verified identity to the session document are committed in one MongoDB transaction. Viewers cannot submit edits, and awareness identity is replaced with server-verified membership. The editor sends semantic commands over Hocuspocus; raw Yjs document updates are rejected. Each edit is validated and transactionally stored as an operation plus the new canonical board/sequence before it is broadcast. A snapshot is stored every 100 accepted operations; session reads replay later contiguous operations and fail closed on a sequence gap. The UI keeps offline commands in session-scoped localStorage and labels them as queued until the server acknowledges a durable commit.

An earlier direct local integration check against configured MongoDB exercised owner verification, session creation, development-mailbox invitation delivery, invitee verification using the same email, explicit invitation acceptance, member session read, and owner session cleanup. It did not verify delivery to an external inbox through the Gmail API. Invitation reuse and owner cancellation have separate feature tests. This was an HTTP/database integration check, not a browser UI pass.

## Exercise local magic-link flow

1. Send `POST /auth/magic-links` with JSON `{ "email": "owner@example.test" }` and an `Origin` header equal to `WEB_ORIGIN`.
2. If Gmail SMTP is not configured, in development on a loopback API host read `POST /__dev/mailbox` with JSON `{ "email": "owner@example.test" }` and the configured web origin. The verification URL is shown only in this local, in-memory inbox; using POST keeps email addresses out of access-log URLs. With Gmail SMTP configured, sign-in links go to the actual inbox instead.
3. Open the link in the Whiteboard app and confirm sign-in. Its verification page reads the token from the URL fragment and immediately removes it from browser history, then `POST /auth/magic-links/consume` with the token and exact `Origin`; it does not consume the token on page load.
4. Confirm the API sets the HttpOnly `wb_session` cookie. `GET /auth/session` returns the verified email identity; `DELETE /auth/session` revokes it.
5. The local mailbox is not email delivery; with Gmail configured, verify sign-in and invitation messages in the actual inbox. Browser confirmation-to-session and reload restoration remain to be checked end-to-end.

## Triage

- **401 on a mutation:** check the browser request `Origin` matches `WEB_ORIGIN` exactly, including scheme and port. Do not broaden CORS to `*` or trust a client-supplied identity.
- **429 rate limited:** limit is 3 requests per normalized email or 10 per source IP per fixed 15-minute window. Honor the `Retry-After` header; inspect rate-limit records by hashed key only. Do not reset counters to bypass abuse controls.
- **503 identity unavailable:** verify API MongoDB connection and indexes. The API must create the feature indexes before it begins listening; if startup failed, inspect index-creation errors. If MongoDB is down, keep sign-in/session claims unavailable until it reconnects; do not fall back to client-generated IDs.
- **No local mail appears:** confirm `NODE_ENV=development`, API binds to `127.0.0.1`, configured `WEB_ORIGIN` matches the caller, and request passed rate limits. Local inbox clears when API restarts.
- **Production email delivery:** currently not configured. Do not expose magic-link sign-in publicly until an approved delivery adapter, verified sender, server-only credential, delivery-failure handling, and abuse controls are configured and validated.
- **Expired or used link:** request a new link. The server rejects links at/after expiry and atomically consumes each link once.

## Signal, threshold, and response

- **Durable edit failure signal:** the API records `Realtime board edit could not be persisted.` with a session id and error class, and the client receives `storage_unavailable` and displays that queued edits are not saved. **Threshold:** any such failure means that particular edit was not accepted; three failures for a session in five minutes are an incident threshold. **Response:** check MongoDB connectivity, transaction/write errors and API health; retain the browser queue, restore DB availability, reconnect, and use Retry queued edits. Do not manually edit operation sequence records or tell participants the change was saved.
- **Shared Undo/Redo failure signal:** the API records `Realtime shared history action could not be persisted.` with a session id and error class; the requesting client receives `storage_unavailable` and states that the shared board was unchanged. **Threshold:** any such failure means that action was not accepted and is actionable; repeated failures across a session indicate Mongo transaction trouble. **Response:** check MongoDB connectivity, transaction/write errors, API health, and whether the operation and history records share the same transaction; ask participants to retry Undo/Redo after service recovery. Do not edit history stacks or sequence records manually. `unsafe_inverse` is an expected user-facing rejection and is not a persistence incident.
- **Semantic command rate signal:** `Realtime semantic command rate limit exceeded.` logs once when a socket crosses 600 commands in 60 seconds; subsequent commands on that window receive `rate_limited`. **Threshold:** one warning is actionable for client diagnosis; repeated warnings from multiple sessions in five minutes suggest abuse or a client loop. **Response:** identify the affected socket/session from server telemetry, stop the runaway client or temporarily disable real-time listener exposure if the burst spans sessions; do not raise the limit without profiling legitimate gesture batching.
- **Snapshot/replay signal:** snapshot writes occur transactionally every 100 accepted operations; replay gaps or missing snapshots fail the board read and room connection, and logs report the session id without board payload. **Threshold:** any gap or unrecoverable snapshot failure is actionable. **Response:** preserve the affected session records for investigation, check replica-set transaction health and indexes, restore from the latest valid snapshot plus contiguous operation records; do not skip a gap or claim the board is recovered.
- **Session end signal:** after the owner-end transaction succeeds, the realtime server closes all sockets tracked for that room with code `4403`; invitation/member records are deleted, followed by operation, snapshot and session records. If cleanup fails, API logs `Ended session cleanup failed; owner can retry the end request.` with `sessionId` and stage (`invitations` or `session_records`), and DELETE returns `503`; the ended marker remains until cleanup completes. **Threshold:** any cleanup failure or any socket remaining after a successful end response is actionable. **Response:** inspect API/MongoDB connectivity and the named cleanup stage, restore DB availability, then retry the owner's end request. Do not reopen the session or manually delete data. A fully cleaned session ID cannot be reused.

- **Realtime lease signal:** structured API log `Realtime seat lease refresh failed three consecutive times; connection closed.` Names only the session id, never the principal, cookie, or token. A failed DB refresh at the 30-second interval increments the connection's consecutive count; success resets it. An expired/missing lease emits `Realtime seat lease expired; connection closed.` **Threshold:** three storage failures (about 90 seconds) close the affected socket; a lease expiry closes it immediately. **Response:** check API-to-MongoDB connectivity and Mongo health, restore the connection, then have the same member reconnect; lease expiry affects socket tracking only and never removes membership.
- **Member-cap signal:** invitation acceptance returns HTTP `409` with a safe session-full message when 25 durable members already exist (owner plus up to 24 invitees). **Threshold:** more than five full-session rejections in 10 minutes for one session merits owner/support review. **Response:** confirm whether a participant should be explicitly removed; do not delete membership records manually. The rejected invite remains pending and can be accepted if a member is removed before expiry.
- **Realtime disconnect cleanup signal:** structured API log `Realtime seat release failed; lease expiry will recover the seat.` **Threshold:** any release failure is actionable because its socket record may remain until lease expiry. **Response:** verify MongoDB write availability; do not delete member records. The 90-second lease bounds stale socket-record retention and does not change who belongs to the session.

- **Rate limit signal:** API response `429` with `rate_limited`; dashboard/structured request telemetry should count these responses without recording email, IP, token, or cookie. **Threshold:** more than 10 such responses from one source IP in 15 minutes or repeated bursts across distinct IPs is actionable. **Response:** check for automated abuse using hashed rate-limit identifiers; keep the limiter enabled, temporarily disable sign-in if abuse continues, then rotate `IDENTITY_RATE_LIMIT_KEY` only if it may be exposed (rotation resets old hashed buckets).
- **Email delivery signal:** API request logs record `503` when the owner has not connected Gmail, OAuth refresh is rejected, Gmail API rejects the request, or the request exceeds 15 seconds. **Threshold:** any invitation delivery `503` is actionable; the pending invitation is canceled and its token is not returned. **Response:** ask the owner to connect/reconnect Gmail, verify OAuth configuration and Google API availability, then resend. Never log/share refresh tokens, OAuth client secrets, recipient addresses, message bodies, invite URLs, or tokens. Delivery is synchronous, so no queue/worker signal or retry runbook applies.
- **Invitation rate-limit signal:** invitation API responds `429`. **Threshold:** more than 10 invitation `429`s from a source IP in 15 minutes or repeated bursts across IPs is actionable. **Response:** inspect hashed limiter identifiers and API request counts, keep the limit enabled, and pause invite creation if abuse continues. Never log invitation URLs, token values, recipient email, IP, or cookies.
- **Participant removal signal:** owner-only DELETE returns `204` after the membership transaction and tracked socket close. A revoked member's later room join/edit is denied; owner roster reports active members and whether each has a tracked socket. **Threshold:** any revoked identity that can still read/edit or reconnect without a newly accepted invitation is actionable. **Response:** inspect membership/session state and the member connection map, close affected room sockets, and preserve audit-safe session identifiers; never restore old membership directly.
- **TTL cleanup:** MongoDB TTL cleanup is asynchronous for pending invitation records, while expiry enforcement is immediate in queries. Acceptance removes the invitation TTL timestamp so durable membership lasts until removal or session end. Inspect expired pending records; if records remain more than 15 minutes past expiry, verify TTL indexes exist and MongoDB TTL monitor health, then use an approved cleanup operation. Never disable exact expiry checks while troubleshooting storage cleanup.

## Limits

Returning members use the authenticated `GET /sessions/mine` request to find active memberships. It returns only session metadata for sessions whose durable member list contains the verified identity, newest activity first; board data is fetched only after a session is selected. If the list request returns `503`, check API/MongoDB availability. If a listed session has since ended or the participant was removed, the subsequent session read returns `404`; refresh the page and do not manually restore membership.

An over-limit persisted board emits HTTP `413 board_too_large` on session creation or a realtime `document_too_large` rejection for edits. The 8 MiB BSON budget is deliberately below MongoDB's per-document maximum. **Threshold:** any occurrence is actionable because the requested state was not persisted. **Response:** tell the participant the shared board is unchanged, reduce unusually large content/strokes, and retry; do not increase the budget without remeasuring both board snapshots and operation/inverse records.

Board operation persistence and repository-level recovery are implemented and passed direct MongoDB integration checks for concurrent ordering, idempotent retry, replay, shared Undo/Redo, Redo-branch clearing, and recovery reads. An authenticated Hocuspocus protocol client committed an edit, the isolated API/realtime process restarted, and a fresh room connection recovered the same board ID, sequence, and edit from MongoDB. A local browser-provider test also queued an offline edit, restarted the isolated API/realtime processes, and verified that the owner reconnected, the queue cleared, and the board retained exactly two objects (no duplicate). Stale-edit conflict behavior and multi-participant browser behavior remain unverified. Owner participant controls and synchronous closure cleanup still need browser/live-socket verification. Sessions have no time-based expiry. Legacy session expiry fields are ignored. Atlas cost and backup-retention settings remain external deployment gates. Do not describe the collaboration system as release-ready until those gates pass.
